# StockTerminal 面试介绍手册

> 用途：面试时被要求"介绍一下这个项目"时的回答脚本 + 追问预案。
> 所有数字均来自本仓库（DEVLOG、docs、tutorial、源码统计），可当场举证，**不要改动或夸大**。

## 0. 先想清楚：这道题在考什么

面试官问"介绍一下你的项目"，实际在同时验证三件事：

| 考察点 | 他想听到 | 常见扣分 |
|--------|----------|----------|
| 你**是否真的做过** | 具体到类名、参数、数字、踩坑现场 | 只会背需求文档，像产品经理 |
| 你**的技术判断力** | 为什么这么选、备选方案是什么、代价是什么 | 只罗列"用了 C++/Qt/SQLite"，像 JD 复读机 |
| 你的**表达与边界感** | 分层递进、能长能短、讲清自己的边界 | 吹大（把规则加权说成 AI、把模拟盘说成实盘） |

**回答策略**：金字塔结构 —— 先给结论（30 秒版本），看对方兴趣再逐层展开（2 分钟 → 5 分钟 → 单点深挖）。
永远"先讲结论和数字，再讲技术细节"，不要从第一天写代码讲起。

**最重要的一个转变**：这个项目最值钱的不是"功能多"，而是几段**工程判断力**的记录（回测口径对齐、内存/O(n²) 优化、堆损坏四轮排查）。
面技术岗时**优先讲这些**，功能清单只用来回答"还做了什么"。

## 1. 三个版本的自我介绍（照着说）

### 1.1 三十秒版 —— HR 初面 / 电话面 / 面试官说"简单说说"

> "我做的是一个 **A 股量化交易工作站**，桌面端，C++17 + Qt 6，约 **7.5 万行代码**（其中约 4.4 万行是生成的拼音字典，业务代码约 2.9 万行），**476 个单元测试**。
> 它把「看盘 → 选股 → 回测 → 模拟盘」串成一条闭环：自己实现了通达信行情协议直连（TCP 私有二进制协议），能拿到全市场 **5200 多只**股票；引擎层有事件驱动回测（对齐聚宽时序、消除未来函数、T+1、五档费率）、**24 个因子**的选股引擎和网格参数优化；界面是自绘 K 线图。
> 最硬的部分有两个：一是**回测口径对齐**——我的回测一开始跑出 433% 的收益率，我花了 7 轮把它收敛到 25.99%，和聚宽的 21.26% 基本对齐；二是**并发与内存优化**，包括把回测的数据结构从 O(n²) 改成 O(n)、排查掉 5 次堆损坏崩溃。"

**要点**：30 秒内必须出现 ①是什么 ②技术栈 ③规模数字 ④一个最有说服力的硬故事 ⑤留钩子。

---

### 1.2 两分钟版 —— 技术面开场（STAR 骨架）

**S（背景）**
> "A 股散户和量化入门者的工具链是割裂的：看盘用一个软件，选股用 Excel，回测用 Python 脚本，模拟盘再换一个平台，而且免费数据源普遍不稳。我想做一个**一体化**的桌面工作站，把这条链路打通，同时借这个项目把 C++ 工程能力、Qt 自绘图形、并发和性能优化完整练一遍。"

**T（目标/约束）**
> "定了四条硬约束：一，**严格分层**，层间只通过纯虚接口耦合，依赖方向永远自上而下，不许反向依赖；二，**Qt 主线程永不阻塞**，所有网络和计算抛到线程池；三，**编译零警告 + 测试先行**；四，**一套策略代码同时跑回测和模拟盘**，不能写两份。"

**A（我做了什么）—— 按层讲，每层给一个"有含金量"的点**
> "架构分六层：UI → Intelligence → Engine → Core → Data → Foundation。
> **数据层**：抽象出 `IDataProvider`，实现了**通达信直连**（TCP 7709 私有二进制协议：报文编解码、心跳、断线重连、8 个主站 failover）、腾讯 HTTP、AKShare 三个源，外面套 `MultiProvider` 做**主源优先、整体回退**（结果为空才切换，绝不拼接，避免价量口径错配）。
> **引擎层**：事件驱动回测 —— 全局时间轴、逐 Bar 驱动 `onBar`、**四步时序消除未来函数**、下一根 Bar 开盘价成交（与聚宽时序对齐）、T+1、五档费率、13 项绩效；策略通过 `IStrategy` 抽象，**回测和模拟盘共用同一套策略、撮合器、费率计算器**。
> **UI 层**：K 线是 QPainter 全自绘（约 1355 行手写），分层渲染，支持十字线、区间统计拖拽、画线、交易标记、筹码分布；全市场股票池 5213 只带拼音搜索。"

**R（结果 + 反思）**
> "结果是：**P0~P10 共 32 轮迭代、213 次提交**，测试覆盖五个层、**最近一轮 476 个用例全绿**，Release 比 Debug 快 **8.4 倍**（300 只 × 12 组参数：454.8 秒 → 54.2 秒）。
> 但我觉得最有价值的不是这些数字，而是**我不再相信漂亮的数字**：回测跑出 433% 时我第一反应是'这一定是错的'，然后一轮一轮查口径；内存想优化时我先写基准程序，结果发现我原本打算改的地方根本不是大头。"

**结尾留钩子**：
> "如果要展开，我最想讲的是**回测从 433% 收敛到 26% 的那 7 轮排查**，或者那个 Release 才崩、Debug 不崩的堆损坏定位过程，看您想听哪个？"

### 1.3 五分钟版 —— 按"一条数据的完整链路"讲（最显功力）

比"按层罗列"更高级的讲法是**跟着一条数据走一遍**：

```
① 搜索框输入 "gzmt"
   → StockSearchIndex 四通道匹配：精确代码 / 名称 / 拼音首字母 / 全拼
     （内嵌 44435 条 Unicode→拼音表，多音字按词覆盖：银行→yh、重庆→cq、西藏→xz）

② 双击开图
   → UI submitIO 到 IO 线程池（主线程不阻塞，立即显示加载态）
   → IDataProvider(MultiProvider) 先走 TDX 主源：单连接 + mutex 串行（协议有请求-响应配对），
     心跳线程 + 轮询线程，断线重连 + 8 个主站 failover
   → 协议细节：K 线单次上限 800 根需分页；报文用专有浮点/变长整数，响应 zlib 压缩
   → 复权：用除权除息（gbbq）因子做前/后复权

③ 数据回来
   → 写线程安全 DataCache；回测场景同时写二进制磁盘缓存（magic "STB1" + version 校验）
   → EventBus（Qt 信号槽）回主线程，K 线图 repaint

④ 点「参数优化」，选全市场 5213 只
   → ParallelBarFetcher 开最多 4 条独立连接并行分片下载（原来串行约 2 万次往返）
   → GridSearch 多组合并行（Release 上限 4 lane）；组合内按回测日期上报子进度，
     用 compare_exchange 做单调汇总 → UI 进度条 + 剩余时间 ETA

⑤ 出结果
   → 结果表 / 热力图双视图，双击最优格回填到回测面板
```

补一句：**"这条链路上每一环我都踩过坑"**，然后从第 3 章挑故事讲。

## 2. 项目全景速查（被追问时随时取用）

### 2.1 这是什么

综合性**股票交易工作站**（A 股，架构预留多市场），纯本地单机、开源、**零遥测**（不收集不上传任何数据），把看盘、选股、回测、模拟交易、资金数据、交易日志、定时任务收在一个程序里。
用户工作流是：**用它跑模拟盘验证策略，真钱交易仍在外部软件手动操作**（这也是"交易日志：模拟 vs 实盘对比"功能的由来）。

### 2.2 规模与技术栈（背下来，注意两种口径）

| 项目 | 数值 |
|------|------|
| 语言 / 标准 | C++17 |
| UI | Qt 6.11.1（MSVC 2022），**自绘** K 线/分时/热力图（QPainter） |
| 构建 | CMake 3.21+ + Ninja + **vcpkg manifest 模式**；presets：default / with-qt / release / release-qt |
| 代码规模（两种口径，别答错） | src 物理行 **约 7.5 万行**；其中 **4.4 万行是生成的拼音字典**（`pinyin.cpp`），**业务代码约 2.9 万行**；tests 约 **7800 行** |
| 源文件 / 静态库 | src 下约 318 个 `.h/.cpp`；6 个静态库 + 1 个主程序 + **25 个 tools_* 诊断工具** |
| 测试 | 5 个 GoogleTest 可执行程序，**496 个用例宏**，最近一轮 **476/476 全绿**（更早一轮 473/473） |

### 2.3 分层与依赖规则

```
UI → Intelligence → Engine → Core → Data → Foundation
```

- 依赖**严格自上而下**，层间通过**纯虚接口**耦合（`IDataProvider`、`IStrategy`、`IFactor`）。
- 跨层异步用 **EventBus**（Qt 信号槽封装）解耦。
- 一句话答"为什么这么分"：**"为了让引擎层能完全脱离 UI 做单测、让数据源可以随时替换而不动上层。"**

### 2.4 线程模型（必被问）

```
WorkerPool  —— CPU 密集型：回测计算、因子计算、网格搜索
IOPool      —— IO 密集型：网络请求、磁盘读写（限并发）
GUI 主线程  —— 只做渲染和事件处理
回传路径：线程池 → EventBus（信号槽）→ 主线程更新 UI
规则：Qt 主线程永不阻塞
```

细节加分点：
- **安全异步"六道防线"**：`QPointer` 存活检查、**世代号（generation/seq）去陈旧**、连接就绪后才拉数据、防重入标志（如 `polling_`）、`WA_DeleteOnClose` + `QPointer` 容器、显式停止定时器；
- 长任务带**进度回调 + ETA**，进度做**单调保护**（`compare_exchange`），避免并行 lane 完成顺序导致进度倒退；
- 排查异步崩溃时用**复现工具**（`tools_quant_repro`）把竞态从"偶发"变成"必现"。

### 2.6 安全与可观测性（容易被忽略但很加分）

- **敏感凭证**：`CredentialStore` 用 **Windows DPAPI（`CryptProtectData`）** 加密 —— 凭证 JSON 整体加密再 Base64 落盘，**密钥绑定当前 Windows 用户**，文件被拷走或换用户都解不开。威胁模型写在 `docs/security.md`（说清"防什么、不防什么"）。
- **日志**：`LogManager` 封装 spdlog，三个 sink（控制台/文件/UI）。细节坑：**跨线程输出要 `QueuedConnection` 回主线程**，且投递目标要用 `QCoreApplication` 实例而不是 `this` —— `LogManager` 可能在 worker 线程首次创建，用 `this` 会导致信号线程归属错误。
- **配置与路径**：`ConfigManager` + `AppPaths` 统一管理配置与 `%APPDATA%` 数据目录。

## 3. 六个"能讲十分钟"的深挖故事（STAR，背熟）

> 面试官问"遇到过什么难题"时，**优先讲 1、2、3** —— 它们体现的是判断力，比"功能多"值钱得多。

### 故事 1：回测收益率 433% → 26%（我最愿意讲的一个）

- **现象**：回测引擎第一次跑双均线策略，总收益 **433%**；同期聚宽同类策略只有 **21%**，**差了 20 倍**。
- **第一反应（这是重点）**：不是高兴，而是 —— **"这个数字太好看了，一定是错的。"**
- **7 轮收敛，每一轮定位一个具体的口径差异**：
  - **第 1 轮：SMA 指标漏掉当前 bar**。更麻烦的是**方向不确定** —— 有时候晚一天反而"躲过"了下跌，所以 433% 是"运气好的滞后"，不是系统性偏差；**单看数字无法判断根因**。
  - **第 2 轮：未来函数（前视偏差）**。策略在当天 `onBar` 里能看到**当天完整 K 线（含收盘价）**，却按**当天开盘价**成交 —— 相当于 09:30 就知道了 15:00 的价格，**穿越 5.5 小时**；在大涨日白赚涨幅，累积成 433% 的虚假收益。验证锚点：**第一笔交易差了 3 天**。
  - **第 3~7 轮**：费率细节、100 股整手、复权价口径、成交价口径……
  - **结果**：**25.99% vs 聚宽 21.26%**，逐笔对比关键时间段的成交数量/价格基本一致。
- **关键技术点（标准答案，背下来）**：消除未来函数的**四步时序** —— 决策时只用"截至上一交易日"的历史，**把"追加今日 bar 到历史"放在最后一步**，而不是最前。
- **诚实收尾（比数字更打动人）**：
  > "项目里我**没有声称'完全一致'，只写'基本一致'**。剩下的差异来自费率细节、复权价舍入规则、数据源差异（TDX vs 聚宽）——**口径不可能 100% 复刻，目标是'大幅接近'，不是'位级一致'**。"
- **金句**：
  > **"回测最大的风险不是跑不通，而是跑出一个漂亮的错数字 —— 它会让你在实盘里亏得很自信。"**

### 故事 2：O(n²) → O(n)——"加线程没用"的真正原因

- **现象**：回测慢，第一反应是上多线程，但加线程几乎没有收益。
- **定位**：瓶颈**不在线程数，在数据结构** —— `BacktestEngine` 每根 bar 都整段拷贝历史（`BarSeries series(hist)`，O(n²)，900 天累计约 **40 万根 bar**）；同时 Debug CRT 的**堆全局锁**让多线程互相拖累（实测 Debug 下 8 线程耗时是单线程的 **2.3 倍**）。
- **修复**：历史改为 `shared_ptr<BarSeries>` + `append()` 增量追加 —— 复制只复制指针（O(1)），复杂度从 **O(n²) 降到 O(n)**。
- **结果**：**8 线程从 123 秒降到 14 秒**，比单线程快 **2.7 倍** —— 并行只有在瓶颈找对之后才产生正收益。
- **收尾**：
  > "这件事和后来全市场内存优化是同一个教训：**优化前先量化，否则你会优化错地方**。我一开始想的是'加线程'和'把结构体改小'，实测之后发现真凶是 O(n²) 拷贝。"

### 故事 3：全市场回测内存爆炸（5213 只 × 876 天）

- **现象**：参数优化选全市场，进度 78% 后停滞、内存飙升。
- **定位**：写了内存基准程序 `tools_mem_bench` 实测（5213 只 × 876 天 = **440 万个 Bar**）：
  - 拉数据阶段峰值 **830MB**（`Bar` 约 96 字节 × 440 万，数据固有成本）；
  - 回测阶段 **1630MB**：时间轴**每个参数组合都值拷贝一份 440 万个 Bar**（约 420MB）+ 每组合 900 份完整 `Portfolio` 快照 + 多 lane 并行再翻倍。
- **方案（三处一起改）**：
  1. **消除拷贝**：时间轴从存 `Bar` 值改成存 `const Bar*`，指向 DataCache 的 `shared_ptr<BarSeries>` → 干掉每组合 420MB；
  2. **按需快照**：加 `keepEquitySnapshots` 配置，批量场景关闭每日完整组合快照，净值单独用 `equityCurve_` 累积（**先确认全项目没有任何消费者读那份快照**，才敢改）；
  3. **限并行度**：并行 lane 上限从"等于核数（16）"压到 **4**（16 lane × 全市场 = 内存 ×16）。
- **验证**：基准程序复测 **回测 76 秒 / 峰值 1628MB**；做了对照实验（保留 vs 关闭快照：1630MB vs 1643MB），确认剩下的大头是 440 万个 Bar 数据本身（约 830MB），**这部分没得省**。
- **加分收尾**：
  > "我最后的结论是**这一轮已经到边际了**。要再降只能改数据结构（按需加载/列式存储），那是另一个量级的改造、收益不匹配 —— 所以我选择**如实把限制写进文档**，并在 UI 上提前提示预估耗时，而不是假装优化掉了。"

### 故事 4：堆损坏崩溃（Release 才崩、Debug 不崩）—— 四轮排查

- **规模**：这类堆损坏事故一共发生了 **5 次**（08-06 三次、08-07 两次），**四轮**排查才彻底解决；Windows 事件日志 `0xC0000374`。
- **轮次 1 —— 线程风暴**：点「量化工作台」直接崩，且**只在 Release、且启动后立刻点才崩**。
  1. 写复现工具 `tools_quant_repro`（循环构造窗口）→ 确认触发条件：**连接未就绪 + 无主线程延迟 = 稳定崩溃**，加任何打点延迟就不崩 → **微秒级竞态窗口**；
  2. 排除：20 并发拉列表不崩、单独构造 10 个面板不崩、Debug 不崩；
  3. **根因**：`ensureConnected` 在未连接/失败状态下，**每次 `executeCommand` 都 spawn 一个 detached 线程重连**。量化工作台一打开，8+ 组件（6 个股票池选择器 + 2 个搜索框）同时提交请求 → **线程风暴** → 多个连接线程并发 `transport_ = std::move(transport)` → use-after-free / 双重释放 → 堆损坏。而代码里预留的冷却字段 `lastConnectAttempt_` **声明了却从没被使用**。
  4. **修复**：失败路径加 **2 秒冷却**；组件侧先等 provider 连接就绪（≤15s 轮询）再拉数据。
- **轮次 2 —— `stopThreads_` 语义错误（关闭时堆损坏）**：组合面板停止后把 `stopThreads_` 重置，导致**关闭窗口的间隙**里，面板定时器又触发任务、spawn detached `doConnect`，而 provider 随后析构 → 线程访问已释放的 `this`。修复：只在 `connect()` 里置 false（重连必须显式 connect），并在 `ensureConnected`/`refreshQuotes` 入口拦截。
- **轮次 3/4 —— 陈旧对象 / ABI 不一致**：类布局变更后**增量构建残留**，出现 `0xc0000409` 假崩 → **clean rebuild** 解决（教训：改了类成员布局就要 `--clean-first`）。
- **最大的一条教训**：
  > "**报错位置 ≠ 出错位置**。CRT 告诉你'关闭时堆损坏'，真正的根因可能是三天前写的一个异步回调。所以偶发崩溃不要靠猜、不要加重试，**先把它变成必现** —— 我写的复现工具，价值比修复本身还大，它让后面每次改动都有回归验证。"
- **沉淀**：把这次经验固化成**异步安全"六道防线"**写进文档（`QPointer`、世代号、连接就绪检查、防重入、`WA_DeleteOnClose`、显式停表）。

### 故事 5：Debug → Release 提速 8.4 倍（会写基准程序）

- **诊断**：先量化再动手 —— 基准程序 `tools_opt_bench`（300 只 × 12 组参数 MACross）：**Debug 454.8 秒 vs Release 54.2 秒，快 8.4 倍**，且最优目标值完全一致（43.67），证明 Release 没有引入数值差异。
- **动作**：新增 `release-qt` preset + `run-release.bat` 作为日常入口；网格搜索进度粒度细化（组合内按回测日期上报，全市场约 900 个进度点/组合），进度从"每组合静默几分钟"变成持续可见。
- **收尾（诚实）**：
  > "全市场 × 90 组参数在 Release 4 lane 下仍要约 1.9 小时，这是计算量的数学必然。我没有假装能优化掉它，而是让进度持续动、提前提示组合数和预估时间，把'看起来卡死'变成'知道要等多久' —— 这其实是**产品体验问题**，不是纯性能问题。"

### 故事 6：2 万次串行网络往返 → 并行分片 + 磁盘缓存

- **根因**：全市场 5213 只串行拉 400 天预热数据、再单独拉一次真实价区间，约 **2 万次 TDX 往返**。
- **方案 A（并行）**：`ParallelBarFetcher` —— 识别主源为 TDX 后建**最多 4 条独立连接**并行下载，股票池按 lane 轮转分片（`for(i=lane;i<n;i+=lanes)`），结果统一写线程安全 DataCache；并行失败自动回退主源；**非 TDX 源自动降级为原串行逻辑**。同时从已拉取的完整区间里收集真实价，**去掉第二次全市场拉取**。
- **方案 B（缓存）**：`BarDiskCache` —— 不复权日线按股票存二进制到 `%APPDATA%/.../bar_cache/raw/`，带 magic `"STB1"` + version 校验、支持按区间过滤读取；覆盖度判断允许 **3 个自然日边界误差**（跨周末）；命中就完全不走网络。
- **亮点**：**"优化必须可回退"** —— 并行不是硬开关，主源不支持时自动走老路，所以风险可控。

### 备选故事：私有协议逆向 + 一个差 100 倍的显示 bug

- **协议侧**：通达信是 **TCP 7709 私有二进制协议**（非公开），参考 `injoyai/tdx`(Go) / `pytdx`(Python) 移植成 C++：报文编解码、msgId 关联、**变长整数与专有浮点格式**、zlib 解压、心跳保活、轮询线程、断线重连 + **8 个主站 failover**。协议本身是请求-响应配对，所以**单连接 + mutex 串行**，不适合单连接并发。
  - 实测细节：服务器**单次报价批上限 80 只**（请求 200 只也只回 80）；K 线单请求上限 800 根需分页。
- **那个 bug**：分时图第一根量柱 1000.95 万 vs 参照软件 10.01 万，**差 100 倍**。实证：逐笔协议（0x0FC5）返回的量**原始单位是"手"**，`getIntraday` ×100 转"股"是对的，问题在**显示层把"股"当"万股"格式化**。修复：统一 `formatVolume()`（股→手自动缩放），量轴/十字线/图例全部接入，并在解码处**加注释防再误读**。
  - 金句：**"单位换算是金融软件的高危区，跨层传数值时，单位必须写进类型或命名里。"**
- **另一个坑（GBK 陷阱）**：行情服务器返回的股票名称是 **GBK** 编码，直接用 UTF-8 解析会乱码/截断，`data/cn_encoding.{h,cpp}` 专门做转换。

## 4. 高频追问 & 回答脚本

### A 类：技术选型（不要说"因为喜欢"）

**Q1：为什么用 C++ / Qt，而不是 Python？量化不都用 Python 吗？**
> "两层原因。**性能上**，全市场 5213 只 × 876 天是 440 万个 Bar 的循环，我自己实测 Debug/Release 就差 8.4 倍，语言层面的差距更大；而且我做了一次数据结构优化（O(n²)→O(n)）就带来 8 线程 123s→14s 的差别，说明**性能在这个场景是真实约束**。**工程上**，我要的是一个**带自绘图表的原生桌面程序**：K 线上要叠指标、画线、交易标记、筹码分布，QPainter 让我完全控制渲染，不被浏览器或图表库绑住。当然 Python 生态（数据、回测框架）更成熟，我把数据源抽象成 `IDataProvider`，要接 Python 研究服务在架构上没有阻碍。"

**Q2：为什么自己写回测引擎？不用 backtrader / vnpy？**
> "三个理由。① 目标是**一体化桌面工具**，引入 Python 运行时让打包部署调试都变复杂；② 我需要**回测和模拟盘共用同一套策略代码**，只有自己控制 `IStrategy` 接口才能做到；③ 回测逻辑（撮合、费用、复权、T+1）不复杂，但**口径正确性要求极高** —— 我为了对齐聚宽花了 7 轮，如果直接用第三方框架，我可能永远不知道那 433% 是怎么来的。"

**Q3：为什么用 vcpkg 和 CMake presets？**
> "vcpkg 用 manifest 模式（`vcpkg.json`），依赖和 feature 声明在仓库里，换机器一个命令还原环境；presets 把 Debug/Release × 是否带 Qt 固化成 `default / with-qt / release / release-qt`。踩过的坑也写进文档了 —— 比如 Release 复用 Debug 的 `vcpkg_installed` 避免重新下载依赖，以及必须显式指定 `CMAKE_CXX_COMPILER=cl`，否则 PATH 里的 mingw64 会让 CMake 误选 GCC，链接期才炸。"

### B 类：架构与设计

**Q4：分层架构怎么落地？怎么保证不反向依赖？**
> "三个手段：① **物理隔离** —— 一层一个顶层目录 + 一个 CMake target（共 6 个静态库），下层拿不到上层的头文件路径，反向依赖**编译期就失败**；② **接口定义在下层** —— `IDataProvider` 在 data 层、`IStrategy` 在 engine 层，上层只依赖抽象；③ **文档与规范固化**（`docs/architecture.md` 写明每层职责与"不依赖"清单）。"

**Q5：要接一个新的数据源，要改多少代码？**
> "**上层零改动**。实现 `IDataProvider` 的 11 个纯虚方法，在 `ProviderFactory` 里注册即可。接口对可选能力做了**默认降级**：`getMarketDepth`（五档盘口）默认返回 `nullopt`、`getRawBars` 默认返回空 —— 只有 TDX 支持的能力不会强迫其他源写假实现。这是我学到的一条接口设计原则：**抽象接口要为"能力差异"留退路，而不是要求所有实现都对等**。"

**Q6：多个数据源怎么保证数据一致？**
> "`MultiProvider` 是**整体替换、绝不拼接**：先看主源是否可用，主源为空或失败才**整体**切备源，**不做字段级合并** —— 不同源的复权口径、时间戳、量纲可能不同，拼接会产生"价格来自 A、成交量来自 B"这种**静默错误**，比直接失败危险得多。内部用三个原子标志（是否接受过连接、是否曾连上、是否已判定不可用）避免每次都先超时再回退。"

**Q7：回测结果怎么保证可信 / 可复现？**（⭐ 这题直接上故事 1）
> "我有一套完整的对齐方法：① **成交假设写死并文档化** —— 昨日收盘出信号、今日开盘成交（聚宽兼容）；② **四步时序消除未来函数** —— 决策时看不到当天 K 线，把"追加今日 bar"放最后一步；③ **用真实价成交** —— 信号用前复权算（指标连续），成交用不复权真实价；④ **warm-up 400 个日历日**预填指标；⑤ **验证锚点是第一笔交易**，不是总收益 —— 我最初就是靠"第一笔差了 3 天"定位到未来函数的；⑥ 最后和聚宽做**逐笔对比**，收敛到 25.99% vs 21.26%，而且我只写"基本一致"，不写"完全一致"。"
> **加分补充**："这里有个反直觉的点：**总收益对不上时，先看第一笔交易对不对**。总收益是几百笔交易的累积，误差会被平滑掉；第一笔交易能立刻暴露时序错误。"

**Q8：T+1、涨跌停、整手这些 A 股规则怎么处理？**
> "T+1 落在持仓结构上：`Position` 增加 `todayBuy`，买入当日计入 `todayBuy`，卖出只能卖 `available`，新交易日自动解冻，**回测和模拟盘共用**。整手按 100 股向下取整。涨跌停价按板块区分（创业板/科创板 20%、其余 10%）。这里有个真实 bug：模拟盘最初直接拿 3 秒一次的实时报价当 K 线，导致一个交易日生成很多根日线、策略信号乱跳 —— 修法是**同一交易日内合并更新同一根日线**。"

### C 类：质量、并发、调试

**Q9：怎么测试有网络依赖的代码？**
> "核心是**把不确定性注入进来**：网络层抽象成 `TdxTransport` 接口，生产用 `TdxSocket`，测试注入 Fake；协议编解码、复权、分页、因子计算这些**纯逻辑单独测**（`test_tdx_protocol` 覆盖报文解析）；依赖外部服务的部分**不写成必绿的假断言**，而是如实标注为既有问题并在文档记录（比如 113 个数据层用例里有 1 个连接恢复时序用例，我会说明它与本次改动无关，而不是删掉或跳过它'变绿'）。并发和随机性则靠**可复现**：回测是确定性的，所以能直接断言数值。"

**Q10：470 多个测试怎么组织的？**
> "按层拆成 5 个 GoogleTest 可执行程序（foundation / core / data / engine / intelligence，另有少量 UI 测试），CTest preset 一键跑。**测试先行**是硬规则：Core/Engine 层先有测试再推进，`build.bat` 里 configure → build → ctest 是一条链，**测试不过不算完成**。"

**Q11：Qt 主线程不阻塞，异步回来 UI 已经销毁了怎么办？**
> "所有网络和重计算都 `submitWorker` / `submitIO`，主线程只渲染。异步回调有**六道防线**：`QPointer` 检查对象存活、**世代号去陈旧**（用户快速切股时旧请求必须丢弃）、连接就绪才发请求、防重入标志、`WA_DeleteOnClose` + `QPointer` 容器管理子窗口、显式停止定时器。这些是硬性规范，不写就算 bug —— 我为此付出过 5 次堆损坏的代价。"

**Q12：项目里有敏感信息吗？怎么存的？**
> "有 —— 数据源 token 和将来的券商凭证。我**不自己发明加密**：用 Windows 的 **DPAPI**（`CryptProtectData`），凭证 JSON 整体加密再 Base64 落盘，密钥由系统绑定当前 Windows 用户，磁盘被拷走或换用户都解不开。另外整个程序**零遥测**：不收集、不上传任何用户数据。同时我在 `docs/security.md` 写清了**威胁模型** —— 它防"文件被窃取/离线读取"，**不防**"攻击者已拿到当前用户执行权限"。把边界写清楚比喊口号有用。"

### D 类：压力与质疑（最需要准备）

**Q13：这个项目是你一个人做的，还是跟着教程/开源项目做的？**（几乎必问）
> "是我独立做的。边界我说清楚：**架构、分层、接口设计、回测与模拟盘引擎、并发与性能优化、UI 是我设计和实现的**；第三方只用库（Qt、spdlog、TA-Lib、GoogleTest），没有基于某个现成项目改。两个诚实的例外：① **通达信私有协议**不是我逆向的，我参考了 injoyai/tdx、pytdx 这些公开实现，自己重写成 C++，并补了心跳、failover、分页、GBK 解码、单位换算这些工程细节；② 仓库里 `docs/tutorial/` 那份 10 模块精读材料，是我**自己整理的复习/教学材料**，用项目代码当教材，不是我的开发依据。"

**Q14：你说的 "AI 智能" 是真 AI 吗？**
> "**不是机器学习模型，我必须说清楚** —— 我不想用模糊的词误导人。我实现的是一套**规则加权的多因子融合**：K 线形态识别、舆情情绪（东财新闻词典打分）、技术指标（RSI/MACD/动量）三路各自归一化到 -1~+1，按 0.4/0.3/0.3 加权，并且**带置信度** —— 置信度 = 分项覆盖度 × 一致度，某个分项没数据时按权重折减覆盖度，**让信号诚实地说"我证据不足"，而不是硬凑一个结论**。需求文档里写的 ML 选股是规划；要上真模型需要标注数据和特征工程，我会作为下一步，而不是包装成已完成。"

**Q15：需求文档里写"50+ 因子""遗传算法""实盘交易"，代码里有吗？**
> "都没有落地，而且我在文档和 README 里**主动标注了**，这是我的技术债清单：因子需求写 50+，**当前落地 24 个**（动量/波动/质量/量价 21 个 + PE/市值）；参数优化实现了**网格搜索 + 热力图**，遗传算法没做；**实盘明确不做**（设计文档里就写了"实盘交易明确不做"，只做模拟盘，券商接口差异大且需要资质）；SQLite 的 `DataRepository` 已实现并有单测，但**未接入主流程**（README 里也是这样写的）—— 当前是内存 + 二进制磁盘缓存。我宁愿你看到真实完成度：**把未完成的写清楚，比假装完成更省事**。"

**Q16：这个项目最大的不足是什么？如果重做你会改什么？**（必问，答不好会致命）
> "四层。
> **架构**：DataRepository（SQLite 持久化）实现了但没接线，导致全市场首次回测每次都要联网拉 K 线（预计 10~30 分钟），这是最大的体验短板。重做我会把持久化放在 P1 就接到主流程，而不是等 UI 做完再补。
> **性能**：全市场网格优化仍是小时级。真正的解法不是抠常数，而是**改计算模型** —— 多组合共享数据快照、回测热路径缓存友好化、参数扫描可增量计算。
> **工程**：我写了 25 个探针/基准程序，它们救过我很多次，但散在 `src/` 下没有统一组织、也没有 CI 门禁 —— 应该收进 `tools/` 并让 CI 定期跑基准防性能回归。另外仓库根目录还残留几个临时 `.obj` 文件，属于**仓库卫生没做好**。
> **方法**：最大的收获是**"先量化，再优化"**。我想砍内存时第一个念头是"把 Bar 结构体改小"，实测才发现大头是"每组合拷贝 440 万个 Bar 的时间轴"——不写基准程序我一定会改错地方。"

**Q17：代码量 7.5 万行（还是 3 万行？），你怎么保证质量？**
> "先澄清口径：**src 物理行约 7.5 万，其中 4.4 万行是生成的拼音字典**（`pinyin.cpp`，由脚本从公开拼音数据生成），**我手写的业务代码约 2.9 万行**，tests 约 7800 行。质量靠四条硬规矩：① **编译零警告**（每次改完必须零错误零警告）；② **测试先行**（Core/Engine 层先写测试）；③ **小步迭代**（一个阶段拆成小任务，每个任务"实现→编译→测试→再推进"）；④ **写 DEVLOG** —— 每轮记录"现象→根因→修复→验证"，**包括没验证完的部分也会写"待手动复测"，不许把没验证的写成已验证**。"

**Q18：你在这个项目里最自豪的是什么？**（送分题，别答成"功能多"）
> "三件事。
> 一是**回测口径对齐**：从 433% 的漂亮错数字，7 轮收敛到 25.99%（聚宽 21.26%），并且我学会了"验证锚点用第一笔交易，而不是总收益"。
> 二是**一套策略代码同时跑回测和模拟盘**，共用 `IStrategy`、撮合器、费率计算器 —— 抽象定得早，后面加多股票模拟盘、T+1 规则都只改一个地方。
> 三是**"先复现、再修"的习惯**：那个 Debug 不崩、Release 偶发的堆损坏，我用复现工具把它变成必现，再用排除法定到连接建立期的线程风暴，最后沉淀成异步安全"六道防线"写进规范。**工具比技术更能决定你解决问题的速度。**"

**Q19：你这个项目做了多久？**（⚠️ 面试官翻 git 会看到提交集中在 2026-08）
> 先确认你自己的真实时间线，**按事实回答**，但答的时候**突出交付密度和方法**：
> "集中的开发是在 8 月，**一个月内 213 次提交、32 轮迭代**（P0 类型系统/线程池 → P10 扩展增强）。节奏是：前期打地基（类型系统、事件总线、线程池、数据源抽象、回测引擎），中期做 UI 与量化面板，后期全部是**优化、对齐和修 bug** —— 最后的 DEVLOG 有 2000 多行，全是"现象→根因→修复→验证"的记录。"
> **不要编造更长的周期** —— 交付密度本身就是优点，编时间线反而会在"哪一轮做了什么"的追问里露馅。
